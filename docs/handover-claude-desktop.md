# 交接：壓測執行與報表做法（給 Claude Desktop 製作客戶簡報）

> **用途：** 讓 Claude Desktop 製作簡報，向證券方說明「壓測怎麼執行、報告怎麼產生、怎麼看」。這份交接是「新阿發 壓力測試規劃 v1.4」的補充，對應 p.14（指標）、p.16（工具與壓測機）、p.17（執行流程）。
> **日期：** 2026-10-11。
> **注意：**
> - 本文件的效能數字都來自**本機 mock 模擬**，只用來說明機制與報告格式，**不能當成系統效能的結論**。
> - 標示「待確認」的項目不要寫成定案。
> - 環境的內部細節（IP、secret 名稱、專案 ID）不要放進簡報。

---

## 1. 一句話摘要

壓測機使用 **k6 原生功能**，在 Cloud Run Jobs 上分成多個 task 平行執行。各 task 把原始數據定時存到 GCS；需要看報告時，手動執行一次報表程式，就會合併**所有壓測機的原始數據**，產出一份可以下載、離線開啟的 HTML 報告。壓測進行中、結束後都可以產生。

## 2. 做法（建議做成 1 張架構圖 + 1 張流程說明）

```
壓測專案（與受測系統不同的 GCP 專案）
  ① Cloud Run Job「壓測機」：N 個 task 平行，各送 1/N 的流量
       每個 task：k6 輸出原始數據 → 每 5 分鐘上傳到 GCS
  ② GCS：存放所有 task 的原始數據、各 task 的 k6 dashboard
  ③ Cloud Run Job「報表」：需要時在 Console 按一下執行
       合併全部原始數據 → 產生 HTML 報告 → 存回 GCS
  ④ 使用者從 GCS 下載報告
流量：壓測機 → Cloud NAT 固定 IP → 受測系統（外部網域 → Load Balancer）
```

**說明重點（客戶看得懂的理由）：**

| 設計 | 理由 |
|---|---|
| 只用 k6 原生功能，不另建監控平台 | 在客戶環境建置的項目最少（Cloud Run Jobs、一個 GCS bucket、Cloud NAT），建置快、壓測後容易整套刪除 |
| 原始數據定時上傳，報告隨時可以產生 | 壓測進行中也能看到「截至目前」的結果，報告最多比實際進度晚一個上傳間隔（預設 5 分鐘） |
| 報告由所有壓測機的原始數據合併重算 | 多台壓測機各自的 p95 不能平均，必須用全部請求重算才正確；已驗證報表數字與 k6 完全一致（見第 4 節） |
| 報告是單一 HTML 檔 | 下載後不需要網路就能開，可以直接附在壓測報告中 |
| 不走 Cloud Logging、不建 BigQuery | Cloud Logging 匯出到 GCS 是每小時批次，壓測中看不到最新結果；數據量大時有被限流的風險；BigQuery 對這個用途沒有必要 |

## 3. 兩種報表：各自看什麼（建議做成 1 張對照表）

| | k6 內建 dashboard | 合併報告（報表 Job） |
|---|---|---|
| 範圍 | 單一壓測機（1/N 流量） | **全部壓測機合併** |
| FAQ／業務查詢分開 | ✗ | ✓ |
| 各加壓階段判定（✓／✗） | ✗ | ✓ |
| 回應時間 p50／p95／p99 | 整體（p50 只在表格） | 整體、各類別、各階段 |
| 錯誤率（5xx + timeout） | 只有總計 | 趨勢圖、各階段 |
| 時間拆解（連線、等待、傳輸） | ✓ | ✗ |
| 用途 | 排查個別壓測機、看時間拆解 | **正式壓測報告的數字來源** |
| 教學說明 | 報表 Job 自動產生教學版（中文說明框） | 閱讀指南、名詞解釋、各區塊說明 |

各圖表怎麼看：見 [dashboard-guide.md](dashboard-guide.md)。

**合併報告的內容：**
1. **總覽：** 送出量、成功量、錯誤率、FAQ／業務 p95、完成對話數。
2. **各階段判定表：** 每個加壓階段（只計持續期間）的每秒請求、FAQ p95、業務 p95、錯誤率、429，對照參考門檻標示 ✓／✗，並列出未通過的項目。
3. **趨勢圖（背景色塊標示加壓階段）：**
   - ① 送出量 vs 成功量
   - ② 回應時間 p50／p95／p99（含負載平衡器 30 秒 timeout 線）
   - ③ FAQ vs 業務 p95（含參考門檻線）
   - ④ 錯誤率（含 0.5% 參考線、5% 停止線）
   - ⑤ VU 數
4. **明細：** 各階段 × 類別的 avg、p50、p90、p95、p99、max、錯誤率、429、業務錯誤。
5. **資料來源：** 各壓測機的狀態（執行中或已完成）與資料截至時間。
6. **警告：** 壓測機不足（dropped_iterations）、出現 429、有壓測機尚未完成。
7. **教學輔助（給第一次看報告的人）：**
   - 頁首「閱讀指南」：三步驟看懂結果
   - 可展開的「名詞解釋」：VU、p50／p95／p99、錯誤率、業務錯誤、持續與爬升期間等 11 個名詞
   - 每個區塊的「怎麼看」說明，右上角按鈕可以一次隱藏（列印或貼進正式報告前使用）
   - 每台壓測機的 k6 dashboard 自動產生教學版：每張圖下方有中文說明，並標明「只代表這台約 1/N 的流量」，可以從報告直接點過去

## 4. 已完成的驗證（本機，2026-10-11）

| 驗證 | 結果 |
|---|---|
| 報表數字正確性 | 同一份原始數據下，報表 Job 算出的 FAQ、業務、開場、登入四類的 p50／p95／p99 與錯誤率，**與 k6 自己算的完全一致** |
| 多台壓測機合併 | 本機同時跑 3 個 task（模擬 Cloud Run 的 3 個 task），各分到約 1/3 流量，合併報告的請求數（5,983）等於 3 個 task 的總和（見 measurements.md M5） |
| 瓶頸呈現 | 刻意調低 mock 容量時，報告正確呈現「2 倍通過、3 倍錯誤率超標」，可以直接判讀觀察到的容量 |
| 壓測中途產生報告 | 壓測進行中執行報表，可以讀取還在寫入中的原始數據，報告標示「資料截至」時間與執行中的 task |
| 原始數據大小 | 每個請求壓縮後約 86～159 bytes；正式規模每個壓測機約 100 MB，記憶體不是問題（見 measurements.md M2、M4） |
| SIT 連線（10/8） | 公司網路可以連到 SIT；k6 無法通過 reCAPTCHA，因此壓測時需要暫時停用（與規劃 p.6 一致） |

## 5. 執行流程中的報表時間點（可以補進規劃 p.17）

| 時間 | 動作 |
|---|---|
| Smoke（T-1） | 執行報表一次，確認報告有數據、各 task 都有上傳；同時量測每台壓測機的記憶體，修正每台能承載的 VU 數 |
| 正式壓測中 | 每個階段結束時可以執行報表，看「截至目前」的各階段判定，作為是否繼續加壓的參考 |
| 每輪結束 | 執行報表，產出該輪最終報告（所有 task 都完成） |
| T+5 壓測報告 | 以各輪的合併報告為數字來源；k6 dashboard 當附件 |

## 6. 限制與待確認（簡報中要標示）

| 項目 | 狀態 |
|---|---|
| 停止條件「連續 3 分鐘」 | k6 的門檻是整輪累計值，無法直接判斷「連續 3 分鐘」；壓測中由人員看報表趨勢圖與 GCP 監控判斷 |
| 每台壓測機可承載的 VU 數 | 試算表假設 4,000 VU／task，**Smoke 時實測修正** |
| 報表處理時間 | 正式規模（一輪約 2,000 萬次請求）的處理時間待實測，預估數分鐘 |
| 報告下載權限 | 有 GCS 讀取權限的人可以直接下載；給其他人要另外產生期限連結，權限設計待與證券方確認 |
| 正式 k6 腳本 | 目前完成的是 mock 版（驗證機制與報告格式）；業務查詢的實際 API 流程、登入流程待確認後開發 |
| 整個機制在 GCP 上的實際部署 | 本機已驗證；容器建置與 Cloud Run 部署尚未執行 |

## 7. 建議簡報結構（4～6 頁）

1. **壓測執行架構：** 第 2 節的架構圖與設計理由。
2. **報告怎麼產生：** 原始數據 → GCS → 按一下產生報告；壓測中也能看。
3. **報告長什麼樣子：** 合併報告截圖，標出各階段判定表與趨勢圖。
4. **兩種報表的分工：** 第 3 節的對照表。
5. **已驗證項目與待確認事項：** 第 4、6 節。
6. （選用）**報告怎麼看：** 摘要 [dashboard-guide.md](dashboard-guide.md) 的重點：p50、p95、p99 的意義、錯誤率定義、壓測機不足的判斷。

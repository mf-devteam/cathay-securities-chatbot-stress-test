# 量測紀錄

試跑與本機模擬的實測結果，作為壓測規劃與後續修正的依據。除非特別註明，數值都來自本機 mock，**不代表任何真實環境的效能**。

| 項目 | 內容 |
|---|---|
| k6 版本 | v2.3.0（Homebrew，darwin/arm64） |
| 本機 | macOS，10 核心、24 GB 記憶體 |
| 量測方式 | 指令與腳本都在本 repo，可以重跑 |

---

## M1. SIT 連線試跑（2026-10-08）

**目的：** 確認從公司網路能否連到 SIT、k6 腳本是否正常、reCAPTCHA 的影響。**詳細結果：** [investigation.md](investigation.md) 第 4.5 節。

| 項目 | 結果 |
|---|---|
| 環境 | 客戶 SIT（客戶環境），公司白名單網路 |
| 腳本 | `k6-poc/script.js`（已移除，見 git 歷史 commit 560a85b）：每 10 秒 1 次，上限 3 分鐘 |
| 實際送出 | 1 個請求（開場問候） |
| 回應 | HTTP 403 E1010（reCAPTCHA 驗證失敗），0.23 秒 |
| 結束方式 | 錯誤率 100%，超過門檻，3 秒內自動中止 |
| 受測系統影響 | BFF 在 reCAPTCHA 檢查就擋下；Middleware 同時段沒有收到任何請求 |
| Dashboard | 執行太短（"not enough data"），**沒有產出 HTML 報告** |

**結論：**
- 網路、腳本、請求格式都正常。
- k6 無法通過 reCAPTCHA（它的設計目的就是擋自動化流量），壓測時需要暫時停用。
- k6 dashboard 需要累積足夠的資料才會產出報告，執行太短（實測數秒）就不會產出。

## M2. k6 原始數據（CSV）大小（2026-10-11）

**目的：** 估算壓測機暫存原始數據需要多少記憶體，以及上傳 GCS 的檔案大小。

| 項目 | 數值 |
|---|---|
| 指令 | `k6 run --out csv=task.csv.gz`（mock、快速模式，1,282 個請求） |
| 每個請求的 CSV 筆數 | 約 12.8 筆（每個 HTTP 指標各一筆，加上自訂指標） |
| 未壓縮 | 約 1,603 B／請求 |
| **gzip 壓縮後** | **約 86 B／請求**（壓縮率約 19 倍） |

mock 的資料重複性高，壓縮率偏好。估算時乘 2，以 **約 170 B／請求** 當安全值。

**依規劃 v1.4 推算一整輪（逐階加壓到 3 倍）：**

| 項目 | 推算 |
|---|---|
| 各階段「佔 1 倍比例 × 持續時間」加總（含爬升） | 約等於 1 倍負載跑 278 分鐘 |
| 聊天 API 總請求數 | 1,239 次／秒 × 278 分鐘 ≈ **2,070 萬次**（不含登入） |
| 全部 task 的 csv.gz 合計 | 約 1.8 GB（安全值 3.6 GB） |
| **每個 task**（3 倍需 35 個 task） | 約 59 萬次請求 → **約 50 MB（安全值 100 MB）** |
| Soak（實測容量 70% × 4 小時，假設容量是 3 倍） | 每個 task 約 130～260 MB |

**結論：**
- 原始數據暫存在記憶體的量很小，相對 32 GiB 的 task 可以忽略。
- **每個 task 的記憶體要以能承載多少 VU 來估**（試算表假設 4,000 VU／task），需要在 Smoke 時實測。
- 一定要用 `.csv.gz`。不壓縮的話每個 task 約 1 GB。

## M3. k6 Web Dashboard 能看到什麼（2026-10-11）

**目的：** 確認規劃 p.14 的指標有哪些能在 k6 原生 dashboard 上看到。**方法：** 解開匯出的 HTML，讀出其中的版面設定與指標清單。

**dashboard 的內容：**
- Overview：5 張圖
- Timings／HTTP：9 張圖。Browser、WebSocket、gRPC 的圖只在有用到時出現。
- Summary：Trends、Counters、Rates、Gauges 四張表

**所有圖表與表格都只取「沒有 tag 的整體值」。**

| 規劃項目（p.14、p.17） | Dashboard | 說明 |
|---|---|---|
| 每秒處理量（送出量） | ✓ | HTTP Request Rate 時間圖 |
| 每秒處理量（成功量） | △ | 自訂指標 `chat_success`，只在 Summary 表有總計 |
| 每秒新開對話數 | ✓ | Iteration Rate（一個 iteration = 一段對話） |
| 回應時間 p95／p99 | ✓（只有整體） | 時間圖有 avg、p90、p95、p99 |
| 回應時間 p50 | △ | 時間圖沒有；Summary 的 Trends 表 `med` 欄有 |
| 錯誤率（5xx + timeout） | △ | 圖上的 Request Failed 含業務錯誤；`errors_5xx_timeout` 只在 Summary 表有總計 |
| **FAQ／業務查詢分開統計** | ✗ | dashboard 不顯示 tag 子指標 |
| **各階段判定** | ✗ | 只有時間軸，沒有分階段的表 |
| **多台壓測機合併** | ✗ | 每個 task 一份，只代表 1/N 負載，無法合併 |
| 停止條件「連續 3 分鐘」 | ✗ | k6 門檻是整輪累計值，只能用延後判定近似 |

**結論：**
- k6 dashboard 適合看整體趨勢，也可以當附件。
- 正式數字由報表 Job（[report-job/](../report-job/)）從原始數據合併重算。機制見 [architecture.md](architecture.md)。

## M4. mock 完整加壓曲線（2026-10-11）

**目的：** 看完整逐階加壓在 k6 dashboard 上的樣子、驗證報表 Job 的計算是否正確、量測真實回應時間分布下的 CSV 大小。**原始輸出：** [samples/2026-10-11-mock-full/](samples/2026-10-11-mock-full/)。

| 項目 | 內容 |
|---|---|
| 設定 | 當時的 mock 腳本 `runner/k6/mock/script.js`（已由正式腳本 [runner/k6/script.js](../runner/k6/script.js) 取代，見 git 歷史）預設值：1 倍 = 1.18 對話／秒（真實的 1/100）、時間 ÷15、思考時間 20 秒、MIX=baseline |
| mock 回應時間 | FAQ／開場平均 9.57 秒、業務 3.5 秒、登入 0.8 秒、容量 150 |
| 執行時間 | 15.5 分鐘（階段 14.5 分鐘 + 收尾 60 秒），正常跑完 |
| 送出／成功 | 7,947／7,927，錯誤率 0.25%，完成對話 530 |
| FAQ 問答 | 702 次，p50 8.56 秒、p95 20.10 秒、p99 27.26 秒 |
| 業務查詢 | 6,235 次，p50 3.07 秒、p95 6.93 秒、p99 9.30 秒 |
| k6 exit | 99（門檻未通過：FAQ p95 超過參考值 10 秒，因為 mock 用的就是 UAT 實測平均 9.57 秒），不是中斷 |
| dropped_iterations | 475（當時 VU 只預先建立 50 個，來不及建立新 VU；已修正，見 M5） |
| **CSV 大小** | **1.26 MB／7,947 個請求 ≈ 159 B／請求**（回應時間較分散，壓縮率比 M2 差，接近 M2 抓的安全值 170 B） |

**報表 Job 正確性驗證：** 用同一份原始數據，報表 Job 與 k6 算出的數字**完全一致**（單位：毫秒）。

| 類別 | 請求數 | p50 | p95 | p99 |
|---|---|---|---|---|
| FAQ | 702 | 8,562.3 | 20,095.3 | 27,260.6 |
| 業務 | 6,235 | 3,073.4 | 6,927.3 | 9,301.2 |
| 開場 | 839 | 8,557.6 | 20,982.5 | 27,144.6 |
| 登入 | 171 | 698.8 | 1,802.9 | 2,164.4 |
| 錯誤率 | — | 兩邊都是 0.2517% | | |

**觀察：**
- **Recovery 階段的每秒請求比預期高。**時間壓縮只套用在階段長度，每段對話仍要 4～5 分鐘，3 倍階段開始的對話在 Recovery 時還在進行。正式（不壓縮）執行時不會有這個問題。
- **Smoke 階段沒有任何請求落在持續期間內。**1 倍的 1% 太低，加上時間壓縮，持續期間內沒有新對話。

## M5. 本機模擬：多 task → 定時上傳 → 合併報告（2026-10-11）

**目的：** 在本機驗證 [architecture.md](architecture.md) 的完整機制。**原始輸出：** [samples/2026-10-11-local-sim/](samples/2026-10-11-local-sim/)。

| 項目 | 內容 |
|---|---|
| 指令 | `RUN_ID=local-sim-20261011 scripts/local-sim.sh` |
| 模擬 | 3 個 task（[runner/entrypoint.sh](../runner/entrypoint.sh)，execution segment 各 1/3）→ 每 20 秒上傳到本機資料夾（模擬 GCS） |
| 設定 | 1 倍 = 2 對話／秒、時間 ÷60、思考時間 3 秒、mock 回應時間 ×0.3、mock 容量 60（讓 3 倍時出現瓶頸）、停止條件關閉 |
| 執行時間 | 4 分 38 秒 |

**結果：**

| 驗證項目 | 結果 |
|---|---|
| 流量分配 | 各 task 1,999／1,989／1,995 次請求，平均分配 |
| 合併正確性 | 3 個 task 的 k6 `http_reqs` 合計 5,983 = 合併報告的 5,983 |
| 壓測中途產生報告（開始後 2 分鐘） | 讀到 3 個 task 寫入中的原始數據共 237 次請求，正確標示 3 個 task 都是 running、報告為「截至目前」 |
| 結束後產生報告 | 3 個 task 都是 finished；各階段判定、趨勢圖、明細正常 |
| 門檻未通過時的 exit code | k6 回 99，runner 改以 0 結束（避免 Cloud Run 重跑壓測） |
| dropped_iterations | 0（M4 的 475 已用預先建立 VU 的估算修正） |
| 報表處理時間 | 5,983 次請求 < 0.1 秒（正式規模待實測） |
| CSV 大小 | 約 158 B／請求（與 M4 一致） |
| **gzip 區塊延遲** | 開始後 1 分鐘內上傳的檔案只有 10 bytes（只有 gzip 檔頭）；約 2 分鐘後出現第一個約 30 KB 的區塊。正式規模流量大，延遲只有幾秒（見 [architecture.md](architecture.md)） |

**各階段判定（最終報告，mock 容量 60）：**

| 階段 | 每秒請求 | FAQ p95 | 業務 p95 | 錯誤率 | 判定 |
|---|---|---|---|---|---|
| 低量 5% | 0.3 | — | 4.00 秒 | 0% | ✓ |
| 低量 10% | 1.0 | 3.37 秒 | 1.42 秒 | 0% | ✓ |
| Baseline 25% | 2.4 | 3.91 秒 | 1.71 秒 | 0% | ✓ |
| 中量 50% | 4.4 | 8.75 秒 | 1.89 秒 | 1.28% | ✗ 錯誤率 |
| 1 倍 | 11.1 | 6.04 秒 | 1.98 秒 | 0.25% | ✓ |
| 2 倍 | 20.3 | 5.60 秒 | 2.29 秒 | 0% | ✓ |
| 3 倍 | 37.4 | 9.00 秒 | 7.42 秒 | 30.50% | ✗ 業務 p95、錯誤率 |
| Recovery 25% | 31.7 | 9.00 秒 | 8.24 秒 | 33.92% | ✗（見下方說明） |

**解讀：** 報告依規劃的判定原則呈現，在這個 mock 設定下：
- **觀察到的容量 = 2 倍。**3 倍時錯誤率明顯超過 5% 的停止條件。
- 3 倍時 p95 被壓平在 9 秒，是 mock 的負載平衡器 timeout（30 秒 × 0.3 倍時間縮放），符合設計。
- **中量 50% 的 ✗ 是偶發錯誤造成的。**樣本少（78 次請求）時，1 次錯誤就超過 0.5%。正式規模樣本多，不會有這個問題。
- **Recovery 沒有回落，是時間壓縮造成的假象**（3 倍時開始的對話還在進行，同 M4 的觀察），不代表系統沒有恢復。
